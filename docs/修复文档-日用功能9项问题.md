# AmberGuard 日用功能问题修复文档

> 基线版本：`v0.5.28`
> 文档状态：代码已落地，待 CI 与双机实测
> 文档目的：修复当前代码中已经确认的 10 个行为、安全、配置与更新机制问题；修复期间不先调整现有阈值数字。
> 适用范围：`D:\OpenCode\AmberGuard`

---

## 1. 现状结论

当前模块的核心日用调度链已经具备可用基础：

- 手动切网保护、家网 BSSID 池、下切/上切防抖和切后短锁已经接入主循环。
- 健康分已经从线性 RSSI 改为分段非线性，并混合 `iw station dump` 的重传率。
- 自动观影保护、失败退避通知和 BSSID 质量记忆已经有配置项、状态字段和 WebUI 入口。
- 本地 `cargo test` 当前通过 21 项。

但以下 10 个问题已经由源码核对确认，不能仅依靠继续调阈值解决：

1. 通知配置字段在 `ConfigPatch` 中声明，但没有真正应用。
2. 自动观影保护的最长时长在持续高流量时不会生效。
3. 关闭自动观影保护不会清除已经生效的自动保护。
4. BSSID 降权会阻断第二候选及后续候选的选择。
5. 裸 `ROAM` 命令接受但最终未落地时不会回退 Framework。
6. 连接命令直接失败时不会进入统一的失败计数和退避流程。
7. 家网以 BSSID 为主键，但链路判断在 BSSID 不匹配时会退回 SSID。
8. 通知通过 `su -c` 拼接 shell 命令，SSID/正文存在命令注入风险。
9. 状态摘要写死 `30/70`，用户调阈值后摘要可能与实际决策不一致。
10. 普通 Magisk 刷包进入 `modules_update` 后，热更新检测和 `service.sh` 没有接管该目录。

本轮修复的原则是：先修行为一致性和安全边界，再用实机日志重新判断阈值是否需要调整。

## 2. 当前阈值基线

以下数值是本轮修复前的现状，修复期间保持不变，作为回归对照：

| 功能 | 当前默认值 | 当前实际含义 |
|---|---:|---|
| 下切健康分 | `< 30` | 偏好频段健康分持续低于下切线后进入下切防抖 |
| 观察线 | `70` | 偏好频段低于此线时增加扫描，不直接切网 |
| 上切 RSSI | `-65 dBm` | 后备频段上只有偏好侧 AP 达到此 RSSI 才允许回切 |
| 同频追优 | 基准 `12 dB` | 当前信号较强时要求更大差值，弱信号时动态收窄到 `5 dB` |
| 下切防抖 | 日用 `4s` | 连续样本满足条件后才下切 |
| 上切防抖 | 日用 `7s` | 后备链路上满足条件后才回切 |
| 省电防抖 | 下切 `7s` / 上切 `12s` | 省电模式降低切换频率 |
| 手动保护 | `60s` | 检测到 SSID 变化后暂不自动抢回 |
| 切后短锁 | `45s` | 成功切换后暂时忽略普通调度，避免被路由踢回 |
| 弱信号断开 | 默认关闭；`-90 dBm` / `15s` | 仅作为最后手段，不是常规切换线 |
| 自动观影触发 | `400 KB/s` / `12s` | 双向 WiFi 流量持续达标后进入自动保护 |
| 自动观影解除 | `<80 KB/s` / `45s` | 流量持续回落后退出保护 |
| 自动保护上限 | `240min` | 计划中的防死锁上限，当前实现有缺陷 |
| BSSID 降权 | 失败 `3` 次 / `1800s` | 失败 AP 软隔离 30 分钟 |
| 失败退避 | `180s` 起，最高 `600s` | 连续失败后暂停继续尝试 |

### 2.1 不属于本轮修改的数字

本轮不修改以下策略：

- 不把 `-65 dBm`、`-80 dBm` 或 `-90 dBm` 宣称为 WiFi 行业统一标准。
- 不把 `400 KB/s` 宣称为“正在观影”的准确识别标准。
- 不新增 SNR、Noise、NL80211 或 Framework Scorer 注入。
- 不改变默认偏好频段、日用/省电/暂停模式和家网安全门控。

## 3. 问题一：通知配置无法保存

### 3.1 现状与证据

文件：`daemon/src/config.rs`

- `ConfigPatch` 已声明 `notify_enable`、`notify_switch`、`notify_weak`、`notify_ongoing_secs`。
- WebUI 的 `saveNotify()` 会提交这些字段。
- `Config::apply_patch()` 在处理 `roam_hold_secs`、`allow_weak_off_home` 和自动观影字段之间，没有把这 4 个通知字段写入 `candidate`。
- 因此 API 可能返回 HTTP 成功，但内存配置和 `config.toml` 仍保持旧值。

### 3.2 最小修法

在 `Config::apply_patch()` 的 clone → patch → validate → swap 流程中补齐 4 个字段：

- `candidate.notify_enable = v`
- `candidate.notify_switch = v`
- `candidate.notify_weak = v`
- `candidate.notify_ongoing_secs = v`，并沿用现有 WebUI 范围或增加明确上限

不得绕过现有原子更新流程，也不得直接修改 `self`。

### 3.3 验收

1. WebUI 关闭通知总开关并保存。
2. `GET /api/config` 返回值变为 `notify_enable=false`。
3. `config.toml` 写入对应值。
4. 重启 daemon 后配置仍保留。
5. 再打开通知总开关，事件通知和常驻通知按各自子开关生效。

## 4. 问题二：自动观影保护最长时长失效

### 4.1 现状与证据

文件：`daemon/src/main.rs`，自动保护分支约在 `1587` 行开始。

当前逻辑在 `auto_soft_active` 为真时，先判断：

```text
traffic < soft_auto_off_kb
```

只有进入低流量分支后才检查 `soft_auto_max_mins`。如果下载或视频持续保持高于解除线，代码每轮把 `until` 刷新为 `now + 30s`，最长时长判断永远不会执行。

### 4.2 最小修法

自动保护处于 active 状态时，每轮都先检查累计时长：

1. `soft_auto_max_mins > 0` 且已达到上限时，先清除自动 `HoldState`。
2. 清除 `auto_soft_active`、`auto_soft_started_at`、高低流量计时器。
3. 记录一次“达到最长保护时长”的日志。
4. 只有未达到上限时，才执行低流量解除和高于解除线的 30 秒续期。

上限只约束自动保护，不影响用户手动点击的固定观影保护。

### 4.3 验收

- 将 `soft_auto_max_mins` 临时设置为最小可测试值，持续制造高于解除线的流量。
- 在高流量不中断的情况下，到达上限后自动保护必须退出。
- `soft_auto_max_mins=0` 时保持“不限时”语义。
- 普通低流量解除仍按 `soft_auto_release_secs` 工作。

## 5. 问题三：关闭自动观影保护不会清除当前保护

### 5.1 现状与证据

文件：`daemon/src/main.rs`，自动保护状态机约在 `1587` 行开始。

当 `soft_auto_enable=false` 时，代码进入“息屏/暂停/关闭”分支，只清除触发计时；如果 `auto_soft_active` 已经为真，则不会清除自动 `HoldState`，也不会把 active 状态复位。

### 5.2 最小修法

配置从开启变为关闭时立即执行一次自动保护清理：

- `auto_soft_active = false`
- `auto_soft_high_since = None`
- `auto_soft_low_since = None`
- `auto_soft_started_at = None`
- 仅当当前 `HoldState` 是 `SoftPause && is_auto` 时清除 hold

不能清除：

- 手动“观影 20 分钟”产生的 hold。
- 手动切网产生的 `Manual` hold。

如果需要识别“刚刚从 true 变为 false”，可增加上一轮配置值；不要按每轮无条件重写手动 hold。

### 5.3 验收

1. 自动保护生效中关闭开关，下一次状态刷新应退出自动保护。
2. 关闭开关不清除手动观影保护。
3. 重新开启后，高流量重新持续满触发时间才进入自动保护。
4. 状态页不再显示 `soft_pause_auto` 或自动观影保护剩余时间。

## 6. 问题四：BSSID 降权会阻断后续候选

### 6.1 现状与证据

文件：`daemon/src/band_bond.rs`，`best_on_band_with()` 约在 `354` 行。

当前流程是：

1. 调用 `best_on_band()`。
2. `best_on_band()` 先返回该频段最强的一个 AP。
3. `best_on_band_with()` 再判断这个 AP 是否在 `demoted` 列表。
4. 如果最强 AP 被降权，直接返回 `None`，不会尝试第二强 AP。

这与文档中“过滤降权 AP 后继续选择其他候选”的设计不一致。

### 6.2 最小修法

把降权条件放进候选筛选阶段，再执行 `max_by_key(signal)`：

- 先按频段、RSSI 门槛、家网 BSSID/stem 规则筛选。
- 对每个候选排除仍在 cooldown 内的 BSSID。
- 最后从剩余候选中选择信号最强者。

优先复用现有 `best_on_band()` 的筛选逻辑；如果为了避免重复实现需要调整函数签名，应保证所有现有调用点和家网限制语义不变。

### 6.3 弱信号特殊边界

如果所有候选都被降权：

- 普通下切/追优保持当前“无目标”行为，不随机放行降权 AP。
- 弱信号救援仍按现有策略决定是否断开，不在本项中偷偷增加降权 AP 兜底。

### 6.4 验收

构造 3 个同频家网 AP：

- 最强 AP 处于降权期。
- 第二强 AP 正常。
- 第三强 AP 正常。

候选必须选择第二强 AP；当三者都降权时才返回 `None`。

## 7. 问题五：裸 ROAM 接受但未落地时不回退 Framework

### 7.1 现状与证据

文件：`daemon/src/main.rs`，切换执行约在 `2160` 行。

同 SSID 切换先执行：

```text
wpa ROAM <bssid>
```

只有 `ROAM` 命令本身返回错误时才调用 `framework_connect()`。如果 wpa 返回 `OK`，但 12 秒内没有真正到达目标 BSSID，代码会记为失败并进入后续失败流程，不会再次尝试 Framework。

这在部分 OEM 上可能表现为 Framework 回滚、忽略裸 ROAM 或短暂断开。

### 7.2 最小修法

把同频切换分成“命令接受”和“落点验证”两层：

1. `ROAM` 返回错误：立即走现有 `framework_connect(ssid, bssid)` 回退。
2. `ROAM` 返回成功但验证超时/目标 BSSID 不匹配：再走一次 Framework 连接。
3. Framework 回退也必须复用现有链路验证，不能把命令返回 `0` 当作最终成功。
4. 两条路径都失败时只记录一次最终失败，避免同一轮重复增加失败计数。

不改变跨频段切换当前以 Framework 为主的路径。

### 7.3 验收

- 模拟或实测 ROAM 返回 `OK` 但 BSSID 不变时，日志必须出现 Framework fallback。
- Framework fallback 成功时，历史结果为成功，不进入失败退避。
- 两次都未落地时，历史只增加一条失败记录。
- 成功后的 `bssid_lock`、通知和 L3 流程只执行一次。

## 8. 问题六：连接命令直接失败未进入统一退避

### 8.1 现状与证据

文件：`daemon/src/main.rs`，切换结果处理约在 `2211` 行以后。

当前有两类失败：

- Framework/ROAM 命令返回成功，但链路最终未落地：会增加 `fail_streak`，达到 3 次后进入长退避。
- Framework 命令直接返回错误：进入 `Err` 分支，只写历史和短 penalty，不增加 `fail_streak`，也不触发 `notify::fail_backoff()`。

因此“命令无法执行、没有 network id、系统未保存网络”等错误可能反复尝试，和“连续失败退避”的用户预期不一致。

### 8.2 最小修法

统一“本次切换尝试失败”的退避计数，但区分质量记忆：

1. 命令直接失败：计入目标级 `fail_streak`，允许触发长退避和失败通知。
2. 命令直接失败不自动记为 AP 射频质量失败，避免把“密码未保存/企业网不可代连”误记为 BSSID 故障。
3. 已发起连接但链路未落地：同时计入目标级 `fail_streak` 和 BSSID 质量记忆。
4. `fail_streak >= 3` 只在从 `<3` 跨到 `3` 的边沿发送一次通知；后续失败只更新退避时间和日志，不重复发同一事件。
5. 退避结束后重新尝试时，仍沿用现有目标键和上限 `600s`。

不要因为统一失败计数而删除现有 `PenaltyLock`；短 penalty 与长退避承担不同层次的抑制作用。

### 8.3 验收

- 让 `framework_connect()` 直接返回错误，连续三次后必须出现长退避和固定 ID 通知。
- 缺少保存密码的错误不会新增 BSSID 降权记录。
- “命令成功但未落地”连续三次仍会新增 BSSID 记忆。
- 第四次失败不新增通知条目，只更新固定退避状态。

## 9. 问题七：家网 BSSID 判断错误退回 SSID

### 9.1 现状与证据

文件：`daemon/src/band_bond.rs`，`link_in_home()` 约在 `58` 行。

当前逻辑：

1. BSSID 命中家网列表，返回 `true`。
2. BSSID 不命中时，如果 SSID 相同，仍返回 `true`。

这与 `home_aps` “BSSID 主键”的设计冲突：同名但未勾选的 AP 可能被当成家网 AP。

### 9.2 最小修法

调整为：

- `home_aps` 为空：仍返回 `true`，表示未启用家网限制。
- 当前状态有非空 BSSID：只按 BSSID 精确匹配；不匹配就返回 `false`。
- 当前状态没有 BSSID：才允许使用 SSID 作为降级判断，并在状态/日志中标明“BSSID 未知”。

SSID 回退只能用于状态源确实没有 BSSID 的情况，不能用于覆盖已知的不匹配 BSSID。

### 9.3 验收

- 已勾选 `HOME_AP_A`，当前连接同名但不同 BSSID 的 AP，状态必须是非家网。
- 当前状态 BSSID 为空但 SSID 相同，保持兼容性降级判断。
- 非家网状态下默认不自动切换、不执行弱信号断开。
- 开启 `allow_weak_off_home` 后，只有明确配置允许时才执行异地弱信号策略。

## 10. 问题八：通知命令存在 shell 注入风险

### 10.1 现状与证据

文件：`daemon/src/notify.rs`，`run_notify()` 约在 `52` 行。

当前流程把参数拼成字符串，再执行：

```text
su 2000 -c "cmd notification ..."
```

现有转义只处理了空格、双引号和反斜杠，没有处理 shell 的 `;`、`&`、`|`、`` ` ``、`$()` 等元字符。通知正文包含 SSID，而 SSID 属于外部输入，因此存在改变 shell 命令语义的风险。

### 10.2 最小修法

优先采用不经过 shell 的执行方式：

1. 探测可用 `su` 路径。
2. 使用 `su` 支持的参数形式，将 uid 和命令参数逐项传递。
3. 如果目标 ROM 的 `su` 只能接受 `-c` 字符串，则实现一个完整的 POSIX shell 单引号转义函数：
   - 每个外部参数都整体包在单引号中。
   - 参数内部的单引号使用 POSIX 标准的 ` '\'' ` 分段转义；不删字符、不执行参数内容。
   - 不对 SSID 或正文做删字符、截断或静默替换。
4. 用纯函数单测覆盖普通 ASCII、空格、中文、单引号、分号、命令替换符和换行。

实现时必须保留 `su 2000 -c` 清除 root capability 的兼容要求；不能退回 `Command::uid(2000)`。

### 10.3 验收

- 含 `;`, `&&`, `|`, `` ` ``, `$()` 和换行的 SSID/通知正文只能作为通知文本出现。
- 不会生成额外文件、执行额外命令或改变通知渠道。
- MIUI/HyperOS 仍能正常发送通知。
- 通知标题去重和固定 ID 覆盖行为不变。

## 11. 问题九：状态摘要写死 30/70

### 11.1 现状与证据

文件：`daemon/src/main.rs`，`status_summary_zh()` 约在 `541` 行。

当前状态摘要内部写死：

- `score >= 70` 显示“良好”。
- `score >= 30` 显示“观察中”。

但实际状态机使用的是配置中的 `score_switch_threshold` 和 `score_detect_threshold`。用户使用“更稳/更敏”预设或手动调整后，摘要可能与真正的切换决策线不一致。

### 11.2 最小修法

给 `status_summary_zh()` 增加实际生效的 `switch_th` 和 `detect_th` 参数：

- `score >= detect_th`：稳定/良好。
- `switch_th <= score < detect_th`：观察中。
- `score < switch_th`：偏弱/可能下切。

`threshold_hint_zh()` 已经使用动态阈值，保持其现有语义，不复制另一套判断规则。

### 11.3 其他动态文案

同时检查以下文案是否仍写死“5G”或 `30/70`：

- 偏好频段标签。
- 上切对照。
- 状态页摘要。
- 阈值页预览。

只修实际与配置冲突的文案，不重新设计 WebUI。

### 11.4 验收

- 将下切线改为 `42`、观察线改为 `78`，状态摘要和阈值对照立即使用新值。
- 恢复默认后回到 `30/70`。
- 切换决策本身不因本项改变。
- 偏好频段切换为 `2.4` 时，文案仍使用“回 2.4G”而非写死“回 5G”。

## 12. 问题十：普通 Magisk 刷包未接入热更新

### 12.1 现状与证据

文件：`daemon/src/main.rs`、`service.sh`、`META-INF/com/google/android/update-binary`

普通 Magisk 更新由安装器执行 `install_module`，新模块会先准备到：

```text
/data/adb/modules_update/AmberGuard/
```

当前运行中的 daemon 位于活动目录：

```text
/data/adb/modules/AmberGuard/bin/amberguard
```

当前实现有三个断点：

1. `module_dir()` 从 `/proc/self/exe` 推导运行中的活动目录。
2. `record_module_mtimes()`、`binary_changed()` 和 `reboot_files_changed()` 都只检查该活动目录，不检查固定的 `modules_update` 候选目录。
3. `service.sh` 在启动时把 `DAEMON` 固定为 `$MODDIR/bin/amberguard`；daemon `exit(0)` 后，脚本仍会用旧活动目录二进制重拉。

本次 diting 实测状态是：

- `modules_update/AmberGuard/bin/amberguard` 已是 v0.5.28。
- 活动目录中的 `bin/amberguard`、`/proc/<pid>/exe` 和 `/api/status.version` 仍是 v0.5.27。
- 没有 `hot update detected`、`exit rc=0` 或新内嵌 WebUI 启动记录。

这不是 v0.5.28 的功能文件天然要求重启。该版本没有改变 `service.sh`、`sepolicy.rule` 和 `post-fs-data.sh`，从运行依赖看属于可以热切换的 daemon/WebUI 更新；问题在于更新机制没有监听标准 Magisk 暂存路径。

### 12.2 目标行为

每次普通刷包后，daemon 和 service 脚本都按以下规则处理：

| 更新内容 | 处理方式 | 用户提示 |
|---|---|---|
| 仅 daemon、内嵌 WebUI、可热替换的面板资源或被动元数据变化 | 使用 `modules_update` 中的新 daemon 重启服务 | 自动重启；新 API/WebUI 可见 |
| `sepolicy.rule`、`post-fs-data.sh` 或 `service.sh` 内容变化 | 保留旧 daemon 运行 | 面板横幅、`update.txt` 和系统通知提示重启 |
| `configResetNeeded=true` | 不自动删除配置 | 明确提示用户重置；保留现有配置直到用户操作 |
| 热更新候选不完整、未稳定或校验失败 | 不切换运行中的 daemon | 记录原因，保留当前运行版本 |

判定不能依靠暂存目录的 mtime。普通刷包会重新生成文件时间，必须对需重启文件做内容哈希或等价内容比较。

### 12.3 最小修法

#### A. daemon 检测两个模块根目录

增加明确的路径角色，不再把运行目录和更新候选目录混为一个 `module_dir()`：

- `current_module_dir`：从 `/proc/self/exe` 得到当前运行目录。
- `update_module_dir`：固定为 `/data/adb/modules_update/AmberGuard`，仅在目录和必要文件完整、候选文件已稳定时作为更新候选。

daemon 每次更新检查应：

1. 检查候选 `bin/amberguard`、`module.prop` 和必要面板资源是否存在且已稳定。
2. 读取候选 `module.prop` 的版本及 `configResetNeeded`。
3. 对 `sepolicy.rule`、`post-fs-data.sh`、`service.sh` 做内容比较，不使用 mtime 判断是否需重启。
4. 纯 daemon/WebUI 更新时记录一次更新事件，写入一次“候选可热更新”状态并正常 `exit(0)`。
5. 需重启或需重置时保持旧 daemon，写入 `update.txt`、状态横幅和通知；同一候选不得每 5 秒重复通知。

“候选可热更新”状态必须是 service 脚本可以消费的明确标记，不能让 service 脚本仅凭“存在 `modules_update` 目录”就启动候选。这样可以避免涉及 SELinux、启动脚本或配置重置的包被错误热启动。

#### B. service.sh 每轮重新选择 daemon

`service.sh` 不能在进入循环前永久固定 `DAEMON`。每次 daemon 退出后重新解析：

1. 只有收到 daemon 写入的“候选可热更新”标记，并且候选文件仍完整时，才启动 `modules_update/AmberGuard/bin/amberguard`。
2. 没有该标记时启动当前活动目录的二进制。
3. 纯热更新的 `exit(0)` 清零崩溃计数，不得触发 `crash limit`。
4. 候选启动失败时清除本轮候选标记，保留当前活动目录版本并记录候选路径和失败原因。
5. 候选 daemon 成功启动后清除一次性标记；后续 daemon 自己负责继续观察是否有更晚的候选更新。

实现中另写入 `/data/adb/amberguard/hot_update_failed` 保存失败候选版本。活动 daemon 看到同版本候选时只记录一次并暂不重试，候选版本变化或用户清理该标记后才重新评估，避免坏候选与活动版本之间反复拉起。

不能通过原地覆盖正在运行的 ELF 实现更新，必须先让旧进程退出，再由 service 脚本启动候选路径中的新进程。

#### C. WebUI 和模块入口边界

根面板由 daemon 编译时嵌入的 `daemon/src/web/static/index.html` 提供，所以 daemon 重拉是 WebUI 热更新的必要条件。`webroot/index.html` 只是 KSU/WebUI 宿主入口；它若发生变化，必须在旧 daemon 退出后同步候选中的安全面板资源，不能只更新内嵌 HTML 后声称整个入口已更新。

候选 daemon 从 `modules_update` 启动时，会将候选 `webroot/index.html` 以临时文件替换方式同步到活动模块的 `webroot/`；候选若未成功启动则不会执行这一步。

`module.prop` 的版本字段和 `action.sh` 等被动入口资源是否立即同步，要与候选分类保持一致；它们不能被用来代替 daemon API 版本判断。至少必须保证：新 daemon 的 `/api/status.version` 和内嵌面板来自同一候选版本。

#### D. 首次启用的引导限制

当前活动版本尚未实现 `modules_update` 候选接管。因此包含本修复的首个版本无法依靠旧版本自动完成自身升级，必须通过一次重启或等价的人工切换先让修复后的 `service.sh` 和 daemon 生效。此后，纯 daemon/WebUI 更新才进入免重启流程。

### 12.4 验收

1. 在旧 daemon 运行时安装一个只改变 daemon/WebUI 的测试包。
2. 确认新文件先出现在 `modules_update/AmberGuard`，旧进程仍可服务当前 API。
3. 候选稳定后日志出现一次 `hot update detected`，旧 daemon 返回 `exit rc=0`。
4. `service.sh` 重新选择候选路径并启动新 daemon，`GET /api/status` 的版本和内嵌 WebUI 均更新。
5. `service.log` 中热更新退出不累计 crash，且没有重复重启或重复通知。
6. 修改候选 `sepolicy.rule`、`post-fs-data.sh` 或 `service.sh` 内容时，不退出旧 daemon，只显示需重启提示。
7. 设置 `configResetNeeded=true` 时，不删除 `config.toml`，只提示用户。
8. 重启后 Magisk 将候选目录提升为活动目录，daemon 仍能正常启动，更新提示被清理。

## 13. 实施顺序

### 阶段 A：先锁住安全和配置行为

1. 修复通知 shell 参数安全问题。
2. 修复 4 个通知配置字段未应用的问题。
3. 增加对应单元测试。

完成条件：通知仍能在两类实机发送，WebUI 通知开关可持久化。

### 阶段 B：修复自动保护状态边界

1. 把自动保护最长时长检查移到低流量分支之外。
2. 关闭自动保护时清除自动 hold，但保留手动 hold。
3. 增加自动保护状态转换测试。

完成条件：持续高流量也能到上限退出，关闭开关立即生效。

### 阶段 C：修复候选与家网边界

1. 降权 AP 在候选筛选阶段排除。
2. 选择第二候选而不是在最强 AP 被排除后直接返回 `None`。
3. 修正已知 BSSID 不匹配时的家网判断。

完成条件：多 AP 家网场景不因最强 AP 降权而放弃正常候选；同名外部 AP 不被误判为家网。

### 阶段 D：统一切换失败闭环

1. 裸 ROAM 验证失败后增加 Framework fallback。
2. 统一命令错误与未落地错误的目标级失败计数。
3. 区分“连接流程失败”和“AP 质量失败”的 BSSID 记忆。
4. 将退避通知限制在第 3 次失败的边沿。

完成条件：每次切换尝试只有一条历史结果，失败不会高频重试，也不会把配置错误误判成 AP 射频故障。

### 阶段 E：状态文案对齐

1. 摘要改用实际配置阈值。
2. 全面检查偏好频段动态文案。
3. 做桌面和移动 WebUI 冒烟测试。

完成条件：状态摘要、阈值对照和实际状态机使用同一组配置值。

### 阶段 F：接入标准 Magisk 更新路径的热更新

1. 抽离当前运行目录与 `modules_update` 候选目录的路径判断。
2. 用内容比较替代需重启文件的 mtime 比较。
3. 让 daemon 产出一次性“候选可热更新”标记，让 `service.sh` 在每轮重拉前重新选择活动或候选 daemon。
4. 接入纯更新、需重启、需重置和候选不完整四种结果的状态提示。
5. 完成一次首个修复版本的引导性重启，再验证后续纯 daemon/WebUI 更新免重启。

完成条件：普通 Magisk 刷包的纯 daemon/WebUI 更新无需手机重启即可切换；启动脚本、SELinux 或配置重置要求仍能明确提示且不误切换。

## 16. 兼容性、持久化与回滚

### 配置兼容

- 新旧 `config.toml` 继续通过 `serde(default)` 读取。
- 不删除现有字段，不改变已有字段含义。
- 新增逻辑只在对应开关或现有功能路径生效。
- 通知字段补齐后，旧配置文件仍使用原默认值。

### 运行时兼容

- 不改变模块监听地址 `127.0.0.1:8080`。
- 不改变 wpa 控制 socket 的发现路径和客户端 bind 规则。
- 不改变 `su 2000 -c` 的通知身份要求。
- 不改变默认 `weak_action=off` 和家网异地保护。
- 普通 Magisk 更新继续使用 `modules_update`，不通过原地覆盖运行中的 ELF 更新。
- 首个包含本热更新修复的版本需要一次重启完成自举；之后的纯 daemon/WebUI 更新按候选目录热切换。

### 回滚

- 每个阶段使用独立 commit。
- 先回滚对应阶段代码，不删除用户的 `config.toml`、`history.json` 或 `bssid_stats.json`。
- 如果切换行为在实机上回归，优先回滚阶段 D；阈值基线保持不变，便于继续分析。
- 如果通知兼容性回归，保留安全转义实现，只回退执行适配层，不退回未转义的命令拼接。
- 如果热更新候选启动失败，保留当前活动 daemon；不得删除活动二进制或把未确认的候选设为唯一启动路径。
